# 🔀 Гайд по вирішенню Git конфліктів

## 📋 Що таке Git конфлікт?

**Git конфлікт** виникає, коли Git не може автоматично об'єднати зміни з різних гілок. Це відбувається, коли:

- Одна і та ж частина файлу змінена в обох гілках
- Зміни в різних гілках суперечать одна одній

## 🔍 Причини конфліктів у вашому випадку

### Конфлікт 1: Docstring

**Причина:** Різні версії docstring в staging та main гілках.

**Рішення:** Об'єднати обидві версії або вибрати найбільш актуальну.

### Конфлікт 2: FastAPI description

**Причина:**

- **Staging:** `"API для агрегації даних про Yield продукти з криптовалютних бірж"`
- **Main:** `"API для отримання даних про Earn продукти з криптобірж"`

**Рішення:** Використати версію з staging (більш точна: "агрегації" замість "отримання").

### Конфлікт 3: Root endpoint

**Причина:**

- **Staging:** Повертає `docs` та `health` поля
- **Main:** Повертає тільки `version`

**Рішення:** Об'єднати обидва підходи - додати всі корисні поля.

### Конфлікт 4: Реєстрація роутерів

**Причина:**

- **Staging:** Використовує `prefix="/api/v1"` при реєстрації роутерів
- **Main:** Не використовує prefix (роутер вже має prefix в routes.py)

**Рішення:** Використати версію з main (роутер вже має prefix, не потрібно дублювати).

## 🛠️ Як вирішити конфлікти самостійно

### Крок 1: Подивитися на конфлікти

```bash
# Перевірити статус
git status

# Подивитися на конфліктні файли
git diff --name-only --diff-filter=U
```

### Крок 2: Відкрити конфліктний файл

Конфлікти позначаються маркерами:

```
<<<<<<< staging
Код з staging гілки
=======
Код з main гілки
>>>>>>> main
```

### Крок 3: Вирішити конфлікт

**Варіант 1: Прийняти версію з staging**

```python
# Видалити маркери та залишити код з staging
Код з staging гілки
```

**Варіант 2: Прийняти версію з main**

```python
# Видалити маркери та залишити код з main
Код з main гілки
```

**Варіант 3: Об'єднати обидві версії**

```python
# Об'єднати код з обох гілок
Код з staging гілки
+ Код з main гілки (додатковий)
```

### Крок 4: Видалити маркери конфлікту

Після вирішення конфлікту **обов'язково** видалити всі маркери:

- `<<<<<<< staging`
- `=======`
- `>>>>>>> main`

### Крок 5: Закомітити вирішення

```bash
# Додати вирішені файли
git add yield-data-service/app/main.py

# Закомітити вирішення
git commit -m "fix: вирішено конфлікти між staging та main"
```

## 📝 Приклад вирішення конфлікту

### Було (з конфліктом):

```python
<<<<<<< staging
    description="API для агрегації даних про Yield продукти з криптовалютних бірж",
=======
    description="API для отримання даних про Earn продукти з криптобірж",
>>>>>>> main
```

### Стало (вирішено):

```python
    description="API для агрегації даних про Yield продукти з криптовалютних бірж",
```

## ⚠️ Важливі правила

1. **Ніколи не залишати маркери конфлікту** - це призведе до помилок
2. **Перевіряти код після вирішення** - переконатися, що синтаксис правильний
3. **Тестувати після вирішення** - перевірити, що все працює
4. **Комітити тільки після повного вирішення** - не залишати часткові вирішення

---

## 🔧 Корисні команди

```bash
# Перевірити конфлікти
git status

# Подивитися деталі конфлікту
git diff

# Прийняти версію з staging для конкретного файлу
git checkout --theirs yield-data-service/app/main.py

# Прийняти версію з main для конкретного файлу
git checkout --ours yield-data-service/app/main.py

# Скасувати merge (якщо щось пішло не так)
git merge --abort
```

---

## 🎯 Стратегія вирішення конфліктів

1. **Прочитати обидві версії** - зрозуміти, що змінилося
2. **Визначити правильну версію** - яка більш актуальна або правильна
3. **Об'єднати якщо потрібно** - взяти найкращі частини з обох
4. **Перевірити синтаксис** - переконатися, що код правильний
5. **Закомітити** - зафіксувати вирішення
