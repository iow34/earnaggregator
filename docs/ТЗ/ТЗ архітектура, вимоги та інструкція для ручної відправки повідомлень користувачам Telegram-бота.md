# Технічне завдання — архітектура, вимоги та інструкція для ручної відправки повідомлень користувачам Telegram-бота

# 1) Мета й сумарні вимоги

* Дозволити адміністраторам/операторам бота вручну відправляти одиночні або масові повідомлення користувачам.
* Можливість **вибору аудиторії** з бази (сегментація: по id, статусу, мові, підписка=on/off, last_active, теги тощо).
* Підтримка типів повідомлень: текст, markdown/html, фото, документ, кнопки (inline keyboard), посилання.
* Надійна відправка з логуванням, повторними спробами, батчингом та контролем швидкості (rate limit).
* Адмін-інтерфейс (веб-панель або бот-інтерфейс) + API/CLI для відправки.
* Безпека: аутентифікація адміністраторів, аудит дій, захист від несанкціонованого broadcast.
* Можливість перевірити доставку / помилки, скасувати розсилку до початку виконання.

(Це загальні вимоги — далі йде технічна розбивка.)

---

# 2) Архітектура — компоненти та зв’язки

1. **Telegram Bot Process** — застосунок, що працює на Aiogram/pyrogram/telegraf/telegram-bot-sdk. Приймає webhook або polling, обробляє оновлення, виконує відправку повідомлень через Telegram API. (Best practice: використовувати бібліотеку, наприклад Aiogram або Telegraf). ([GitHub][1])

2. **Адмін-панель (Web UI)** — SPA/SSR (React/Vue/Next/Django admin) з авторизацією для адміністраторів. В UI: форма створення повідомлення, вибір фільтра/аудиторії, попередній перегляд, кнопка «Send» / «Schedule», лог розсилок. Приклади готових рішень/трендів: TeleAdminPanel, різні aiogram templates з інтегрованою адмінкою. ([GitHub][2])

3. **API шлюз / Control service** — бекенд (FastAPI / Django / Express) приймає запити з UI, валідирує їх, створює запис розсилки у БД, ставить завдання у чергу (RabbitMQ/Celery/Redis+Bull) і повертає результат. (Рекомендується розділити UI-частину й фактичну відправку.)

4. **Queue / Worker(s)** — worker-процеси, які беруть пачки користувачів з черги й викликають методи bot.sendMessage/sendPhoto та обробляють помилки/ретраї. Використовувати батчинг (наприклад, 50–200 повідомлень за підхід) і throttling, щоб не перевищити ліміти Telegram і уникнути блокувань. Бачив реалізації з Bull (Node) та Celery (Python). ([GitHub][3])

5. **Database** — зберігає користувачів, профілі, статус підписки, теги, історію розсилок, логи повідомлень (delivery status, error code). Можливі варіанти: PostgreSQL (реляційна), або MongoDB (документна) для гнучкої сегментації. Є приклади BroadcastBot з MongoDB. ([GitHub][4])

6. **Monitoring / Retry / Audit** — зберігання логів розсилок, метрики (успіх/помилки), retry policy (exponential backoff для тимчасових помилок), можливість manual resume/stop. Також зберігати коментарі оператора.

# 3) Схема бази даних (мінімальна — рел. модель)

**users**

* id (pk, serial)
* telegram_id (bigint, unique) — chat id
* username (text, nullable)
* first_name, last_name
* language (varchar)
* is_subscribed (bool)
* tags (jsonb / array) — наприклад ["paid","trial","active"]
* last_active_at (timestamp)
* created_at, updated_at

**broadcasts**

* id
* author_admin_id
* title
* content_type (text/photo/document)
* content_payload (json/jsonb) — текст, file_id тощо
* filter_query (jsonb) — збережений фільтр (напр. {is_subscribed:true, tags: ["paid"]})
* status (draft|scheduled|running|completed|cancelled|failed)
* scheduled_at (timestamp nullable)
* created_at, updated_at

**broadcast_recipients**

* id
* broadcast_id (fk)
* user_id (fk)
* status (pending|sent|failed|skipped)
* telegram_message_id (nullable)
* error_code (nullable)
* attempts (int)
* last_attempt_at (timestamp)
* created_at

**admin_users**

* id, login, password_hash, role (operator/admin), api_key (optional), last_login

Логіка: при натисканні «Send», бекенд створює broadcast і для вибраної вибірки користувачів записує broadcast_recipients з status=pending; worker читає pending рядки пачками й відправляє.

# 4) Детальний робочий процес (step-by-step) — що відбувається при ручній відправці

1. Адмін заходить в адмін-панель → натискає «Create message».
2. Заповнює: заголовок, текст (формат: markdown/html), додає медіа (файл або file_id), обирає inline keyboard (опціонально).
3. Обирає аудиторію:

   * вручну: ввести telegram_id або username (один/кілька);
   * за фільтром: is_subscribed=true, tags містить "paid";
   * за SQL/JSON запитом (read-only для досвідчених операторів);
   * або завантажити CSV зі списком telegram_id.
4. Можливість «preview» — надіслати тест-повідомлення на тестовий чат (admin або QA chat_id).
5. Натискає Send або Schedule (вкажіть дату/час). UI відправляє POST /broadcasts зі всіма параметрами.

**Backend flow:**
a. Перевірка авторизації та прав (role).
b. Створення broadcast row + запис recipients (bulk insert).
c. Якщо immediate: поставити job у чергу (наприклад, queue.push({broadcast_id})).
d. Worker отримує broadcast_id → читає recipients WHERE status='pending' LIMIT BATCH_SIZE → для кожного викликає sendMessage API → оновлює статус (sent/failed).
e. Якщо помилка мережі/тимчасова (5xx або 429), робити retry із backoff; якщо помилка permanent (403, 400), відмітити failed і зберегти код.
f. Після опрацювання всіх recipients — змінити broadcast.status→completed.

(Цю архітектуру реалізують в багатьох opensource проектах: aiogram templates, telegraf broadcast, Django-based bot templates). ([GitHub][5])

# 5) Rate-limit, батчинг і керування чергою

* Telegram API має ліміти; краще керувати throughput: наприклад, обмеження відправки на одного бота — ~30 повідомлень/сек в загальному (орієнтир — залежить від типу повідомлень). Тому:

  * використовувати **батч розміру** (наприклад 50–200) і queue workers (N workers),
  * застосувати throttling: наприклад pause 0.1–0.5 s між повідомленнями або використовувати token bucket,
  * для великих розсилок — розподілити на кілька workers/інстансів і використовувати backoff на 429 помилки.
* При великих базах (100k+ користувачів) — запускати розсилки не в режимі single process, а через чергу з розділенням на партії. Є готові підходи з Bull (Node) і Celery (Python). ([GitHub][3])

# 6) Безпека та відповідність (обов’язкові пункти)

* **Авторизація**: admin UI має двофакторну авторизацію або довгі API ключі; логін/пароль + ролі.
* **Аудит**: реєструвати хто і коли надіслав повідомлення (admin_user_id) + зміни (edit/delete).
* **Оп-out**: зберігати прапорець is_subscribed; всі розсилки мають поважати unsubscribe (ігнорувати користувачів з is_subscribed=false).
* **Попередній перегляд**: тестовий канал для перевірки форматування перед відправкою широкій аудиторії.
* **Rate/Cost guard**: додаткове підтвердження для великих розсилок (>N користувачів) — підтвердження другого рівня (owner).
* **Захист від помилок**: можливість rollback/cancel перед початком виконання; UI має попереджати про irreversible actions.

# 7) Логування та моніторинг

* Зберігати статус кожного recipient (pending/sent/failed) + error_code.
* Метрики: messages_sent_per_minute, errors_per_minute, average_latency, progress % по broadcast.
* Notification для оператора у разі аномалій (наприклад, spike помилок).
* Dashboard: поточні/завершені розсилки, фільтрація по автору/даті/статусу.

# 8) Інструкція для адміністратора — як вручну відправляти повідомлення

**Варіант A — Web UI (рекомендований):**

1. Зайдіть в адмін-панель → увійдіть під своїм обліковим записом.
2. Menu → Broadcasts → Create New.
3. Заповніть:

   * Title: «Оновлення продукту»
   * Content type: Text
   * Message: вкажіть текст (підтримка markdown/html)
   * Add media: за потреби (завантажте або вставте file_id)
4. Оберіть аудиторію:

   * Quick filters: «All subscribed», «Paid», «Active last 30 days», або
   * Advanced: додайте SQL/JSON фільтр (наприклад `{ "is_subscribed": true, "tags": ["paid"] }`), або
   * Upload CSV: файл з telegram_id у колонці `telegram_id`.
5. Preview → надішліть тест на свій telegram_id (кнопка Send Test).
6. Якщо все ок → Send now або Schedule (вказати дату/час). При великих аудиторіях підтвердження другого рівня.
7. Переглядайте прогрес у Broadcasts → Details → Progress / Errors. Можна зупинити/скасувати, якщо broadcast.status = running.

**Варіант B — Через CLI / API (швидкий для технічних операторів):**

* Відправити POST /api/broadcasts з body:

```json
{
  "title":"Quick notice",
  "content_type":"text",
  "content_payload":{"text":"Текст повідомлення <b>важливе</b>"},
  "filter_query":{"is_subscribed": true, "tags":["trial"]},
  "scheduled_at": null
}
```

* Після успішної відповіді API повертає broadcast_id. Можна перевірити статус GET /api/broadcasts/{id}/status.

**Варіант C — Через бот (не UI):**

* Якщо проект має адмін-bot UX (команди /send, /broadcast), тоді:

  1. /send → введіть telegram_id або оберіть фільтр → введіть текст → confirm.
  2. Система створює broadcast та запускає процес.

(Багато відкритих проектів саме так і роблять — або через веб-панель, або через admin-bot commands). ([GitHub][6])

# 9) Обробка помилок і retry policy (рекомендація)

* Permanent errors (403 Forbidden, 400 BadRequest for chat not found): не повторювати; відмітити як failed і зберегти reason.
* Transient errors (429 Too Many Requests, 500 Internal): retry з exponential backoff (наприклад 3–5 спроб: 1s, 5s, 20s, 60s).
* При 429 — повинен дотримуватись `retry_after` в тілі відповіді Telegram (якщо присутній).
* Логувати детально: trace_id, worker_id, broadcast_id, recipient_id.

##  Приклади з GitHub + аналіз + додаткові правила

Ось кілька відкритих проектів на GitHub, які містять функціональність «broadcast / масові розсилки» або можуть слугувати шаблоном для реалізації твоєї системи:

### Приклади з GitHub

1. **NACBots / BroadcastBot**

   * Репозиторій: `NACBots/BroadcastBot` ([GitHub][1])
   * Особливості:

     * Використовує **Pyrogram / PyroBlack** для взаємодії з Telegram API. ([GitHub][1])
     * Зберігає користувачів у **MongoDB**. ([GitHub][1])
     * Реалізовано **семафор** (semaphore) для контролю одночасних відправлень, тобто обмеження concurrency — це дає можливість безпечно надсилати багато повідомлень одночасно, не «ламаючи» бот чи не отримуючи flood. ([GitHub][1])
     * Є оновлення статусу broadcast в режимі реального часу — адмін може бачити прогрес. ([GitHub][1])
     * Параметри конфігурації, такі як `MAX_CONCURRENT` (максимальна кількість одночасних повідомлень), `UPDATE_INTERVAL` (інтервал оновлення статусу) — вони дозволяють налаштувати розсилку під навантаження. ([GitHub][1])
     * Можливість вмикати / вимикати розсилки через `/settings` — користувачі можуть самі вирішувати, чи отримувати broadcast. ([GitHub][1])
   * Чому корисно: це близький до твоєї задачі приклад — має broadcast, сегментацію (через налаштування), логіку контролю concurrency, реальний моніторинг розсилки.

2. **m4mallu / broadcast-bot**

   * Репозиторій: `m4mallu/broadcast-bot` ([GitHub][2])
   * Особливості:

     * Дуже простий бот, але реалізує базовий функціонал: адміністратор може через самого бота надсилати повідомлення (текст або медіа) людям, які підписалися. ([GitHub][2])
     * Користується PostgreSQL (чи інша БД через `DB_URI`) для збереження підписників. ([GitHub][2])
     * Авторизовані користувачі (admin) задаються через змінні конфігурації (`AUTH_USERS`), таким чином обмежується, хто може робити розсилку. ([GitHub][2])
     * Підтримка медіа — можна надсилати фото чи інші файли. ([GitHub][2])
   * Чому корисно: дуже легка архітектура, яку можна брати за основу або як «мінімальний робочий приклад», якщо потрібно просто базовий broadcast.

3. **moladzbel / mb_support_bot**

   * Хоча це не «broadcast-бот» саме в чистому вигляді, у цьому проекті реалізовано, що **адміни можуть відправляти повідомлення всім користувачам** через support-чат. Репозиторій описаний в коментарях спільноти. ([Reddit][3])
   * Особливості:

     * Використовується **Aiogram + SQLAlchemy** (або подібні ORM) для зберігання стану і користувачів. ([Reddit][4])
     * Існує адмін-група / чат, через який адміни можуть ініціювати масове розсилання. ([Reddit][3])
     * Логи (наприклад, активність, статистика розсилок) записуються, є механіка аудиту. ([Reddit][3])
   * Чому корисно: цей проєкт показує, як поєднати функцію підтримки (support) + broadcast — може бути корисно, якщо хочеш, щоб адміністратор-бот був простим «каналом зв’язку» з усіма користувачами або частиною системи підтримки.

4. **zavidnyi / telegram-scheduler-bot**

   * Репозиторій: `zavidnyi/telegram-scheduler-bot` ([GitHub][5])
   * Особливості:

     * Бот на **Aiogram**, який вміє планувати події (“schedule”), тобто має механіку задач, cron-джобів, що можуть виконуватись у майбутньому. ([GitHub][5])
     * Використовує механізм збереження юзерів (хоча в JSON, не реляційна БД), але архітектурно показує, як комбінувати “відкладену задачу” з ботом. ([GitHub][5])
   * Чому корисно: це хороший приклад для **планування відправки (schedule)**, тобто як реалізувати функцію “надсилати розсилку у заданий час”.

## Додаткові правила й рекомендації до ТЗ (на основі аналізу GitHub-проектів)

На підставі вивчення цих репозиторіїв додаю важливі **принципи, правила та рекомендації**, які варто включити у ТЗ, щоб реалізація була надійною, гнучкою та масштабованою.

1. **Concurrency і контроль навантаження**

   * Використовуй обмеження одночасних відправлень (semaphore або pool), як у BroadcastBot від NACBots — це дозволяє уникнути перевантаження бот-процесу й лімітів Telegram. ([GitHub][1])
   * Налаштовуй параметри “максимальна кількість конкурентних задач” (`MAX_CONCURRENT`) в конфігурації, щоб можна було адаптуватися до різних навантажень і розмірів розсилок. ([GitHub][1])
   * Визнач інтервали для оновлення статусу розсилки (наприклад “update interval”) — щоб адмін не отримував занадто рідкі або занадто часті оновлення, і це не створювало зайвого навантаження. У BroadcastBot це зроблено через конфіговий параметр. ([GitHub][1])

2. **Гнучка база користувачів**

   * Зберігай користувачів у БД, яка підтримує гнучкі фільтри: MongoDB (як у BroadcastBot NACBots) або іншу БД, яка дозволяє зберігати теги, статус, конфігурації підписки. ([GitHub][1])
   * Забезпеч механізм opt-in / opt-out: як в NACBots, юзери повинні мати команду або налаштування, щоб вимкнути розсилки (наприклад через `/settings`). ([GitHub][1])
   * Включай логіку бану або виключення користувачів: репозиторій NACBots дозволяє банити / розбанювати користувачів через адмін-команди. ([GitHub][1])

3. **Безпека адмін-функцій**

   * Адміністраторські команди в боті повинні бути захищені: як у `m4mallu/broadcast-bot`, там список авторизованих user_id (`AUTH_USERS`). ([GitHub][2])
   * Для веб-адмін-панелі або API — реалізуй ролі (наприклад: “оператор”, “глава / власник”) з різними правами (коли великий broadcast, підтвердження другого рівня).
   * Зберігай лог дій адмінів: хто створив broadcast, змінив, скасував, коли і з якою аудиторією — для аудиту.

4. **Моніторинг і статус розсилки**

   * Використовуй підхід зі статусом розсилки (pending, running, completed, failed), як це зроблено в прикладах broadcast-систем — щоб мати чітке уявлення про прогрес.
   * Оновлюй статус в режимі реального часу або з інтервалом (як в NACBots) — конфігуруй “update interval” для балансу між частими оновленнями і системним навантаженням.
   * Логуй помилки доставки: наприклад, якщо користувач відписаний, заборонив бот, помилки API — зберігай код помилки, число спроб, час останньої спроби.

5. **Планування відкладених розсилок**

   * Підтримуй розклади (schedule): за аналогією з “telegram-scheduler-bot” на Aiogram, потрібно мати можливість відправляти broadcast в майбутньому в заданий час. ([GitHub][5])
   * При плануванні зберігай час “scheduled_at” у записах broadcast, щоб workers могли запускати job лише в потрібний момент.
   * Перш ніж запускати великий scheduled broadcast, забезпеч тестову функцію (preview + тестове повідомлення) — щоб уникнути помилок форматування або логіки.

6. **Конфігурованість**

   * Використовуй конфіг-файли / змінні оточення для налаштувань, які можуть змінюватись: `MAX_CONCURRENT`, інтервали оновлення, параметри бази даних, список авторизованих адмінів (ID), ліміти retry. Приклад — у NACBots вони це роблять через конфігурацію. ([GitHub][1])
   * Дозволь гнучкий вибір бекенда бази: можна підтримати MongoDB, PostgreSQL тощо залежно від масштабів проекту.

7. **Помилки та retry**

   * Реалізуй retry із backoff: якщо надсилання повідомлення користувачу не вдалося (тимчасова помилка, rate limit), повторюй з інтервалом, як це часто робиться у продакшн-ботах для масових розсилок.
   * Після декількох невдалих спроб (наприклад, 3–5) — відмічай користувача або broadcast_recipient як “failed” і більше не спробуй (щоб не зациклюватись).
   * Для помилок 429 (“Too Many Requests”), обов’язково враховуй поле `retry_after` з відповіді Telegram API, щоб пауза відповідала рекомендаціям API.
