### Технічне Завдання (ТЗ) на Реалізацію Системи Трекінгу Дій Користувачів у Telegram-Боті


#### Частина 1: Загальний Огляд Системи Трекінгу та Архітектура

**1.1. Мета Системи**  
Система трекінгу призначена для повного моніторингу воронки користувача: від джерела входу в бот (рекламні пости в x.com або інших ресурсах) до взаємодій з реферальними посиланнями на біржі (наприклад, Binance, Bybit, Nexo). Це дозволить збирати дані для аналітики, такі як ефективність рекламних кампаній, поведінка користувачів у боті та конверсія кліків у реферали. Система повинна забезпечувати:  
- Точність даних (без втрат подій).  
- Безпеку (хешування user_id для уникнення витоків даних).  
- Масштабованість (підтримка великої кількості користувачів без затримок).  
- Інтеграцію з існуючою архітектурою (Data Service на FastAPI, Telegram Bot Service на Aiogram 3.x, БД PostgreSQL).  

**1.2. Ключові Компоненти Системи**  
Система складається з таких елементів:  
- **Deep Linking у Telegram:** Для трекінгу джерела входу (рекламні посилання).  
- **Власний Redirect Server:** Для трекінгу кліків на реферальні посилання бірж (проміжний сервер, який логує дані перед редіректом).  
- **База Даних (PostgreSQL):** Центральне сховище для всіх трекінгових даних, з таблицями для користувачів, джерел, кліків та аналітики.  
- **Інтеграція з Ботом:** Генерація динамічних посилань у повідомленнях бота на основі сторінок (сторінка 1: /start, сторінка 2: продукти біржі, сторінка N: список бірж).  

**1.3. Загальна Архітектура**  
- **Потік Даних:**  
  1. Користувач клікає на рекламне посилання (наприклад, t.me/YourYieldBot?start=ad_xcom_campaign123) → Бот обробляє deep link → Зберігає джерело в БД.  
  2. У боті на сторінках (1, 2, N) генеруються динамічні реферальні посилання через redirect-сервер (наприклад, https://your-domain.com/ref?user=hashed_id&source=ad_xcom_campaign123&exchange=binance&page=1).  
  3. Користувач клікає → Redirect-сервер логує дані (user_id, source, page, exchange, timestamp, IP) у БД → Редірект на біржу.  
  4. Дані в БД доступні для аналітики (агрегація по кампаніям, користувачам, біржам).  

- **Правила Інтеграції з Існуючою Архітектурою:**  
  - Data Service (FastAPI): Розширити для хостингу redirect-endpoint та API для аналітики (наприклад, /analytics?campaign=123).  
  - Telegram Bot Service (Aiogram): Додати хендлери для deep linking та генерації посилань.  
  - БД PostgreSQL: Додати нові таблиці (деталі нижче).  
  - Хостинг: Використовувати Railway або Fly.io для redirect-сервера; забезпечити HTTPS для безпеки.  
  - Безпека: Хешувати user_id (SHA-256); не зберігати чутливі дані (токени бірж) у логах; використовувати rate-limiting на redirect для захисту від DDoS.  

**1.4. Вимоги до Даних, Які Збираються**  
- **Джерело Реклами та ID Кампаній:** З deep link (payload формату "ad_platform_campaignID", наприклад "ad_xcom_nov2025_123").  
- **Кліки по Біржах:** Для кожного кліку збирати: hashed_user_id (хешований Telegram ID), source (джерело входу), page (1, 2 або N), exchange (назва біржі, наприклад "binance"), timestamp (час кліку в UTC), ip_address (IP користувача для гео-аналітики), user_agent (браузер/пристрій для сегментації).  
- **Додаткові Правила Збору Даних:**  
  - Логувати тільки унікальні кліки? Ні, логувати кожен клік (для підрахунку повторних взаємодій).  
  - Якщо користувач входить без deep link — source = "organic".  
  - Підтримка множинних кліків: Один користувач може клікати на різні біржі з різних сторінок.  
  - Обробка помилок: Якщо redirect не вдається (наприклад, невалідні параметри) — логувати помилку в окрему таблицю logs.  

**1.5. Структура Бази Даних для Трекінгу**  
У PostgreSQL створити такі таблиці (розширити існуючий Database Layer):  
- **Таблиця users:**  
  - id (SERIAL PRIMARY KEY)  
  - telegram_id (BIGINT UNIQUE) — оригінальний ID для внутрішнього використання.  
  - hashed_id (VARCHAR(64) UNIQUE) — хеш SHA-256 від telegram_id.  
  - acquisition_source (VARCHAR(255)) — джерело входу (наприклад, "ad_xcom_nov2025_123").  
  - joined_at (TIMESTAMP) — час реєстрації.  
  - last_activity (TIMESTAMP) — оновлюється при кожній взаємодії.  

- **Таблиця clicks:**  
  - id (SERIAL PRIMARY KEY)  
  - hashed_user_id (VARCHAR(64) REFERENCES users(hashed_id))  
  - source (VARCHAR(255))  
  - page (VARCHAR(50)) — "1" (головна), "2" (продукти біржі), "N" (список бірж).  
  - exchange (VARCHAR(100)) — назва біржі (lowercase, наприклад "binance").  
  - timestamp (TIMESTAMP) — час кліку.  
  - ip_address (VARCHAR(45)) — IPv4/IPv6.  
  - user_agent (TEXT) — рядок агента браузера.  
  - ref_code (VARCHAR(100)) — реферальний код біржі (для перевірки).  

- **Таблиця campaigns:**  
  - id (SERIAL PRIMARY KEY)  
  - campaign_id (VARCHAR(100) UNIQUE) — ID кампанії (наприклад, "nov2025_123").  
  - platform (VARCHAR(50)) — "xcom", "telegram_ads" тощо.  
  - start_date (DATE)  
  - end_date (DATE)  
  - description (TEXT) — опис кампанії для аналітики.  

- **Таблиця logs:**  
  - id (SERIAL PRIMARY KEY)  
  - event_type (VARCHAR(50)) — "error", "warning".  
  - message (TEXT)  
  - timestamp (TIMESTAMP)  

**1.6. Правила Масштабування та Оптимізації**  
- Індексація: Додати індекси на hashed_user_id, source, timestamp у таблиці clicks для швидких запитів.  
- Очищення Даних: Щомісяця архівувати старі кліки (>6 місяців) у окрему таблицю archive_clicks.   
- Тестування: Перевірити на тестових користувачах: симулювати входи з deep link, кліки з різних сторінок, перевірити записи в БД.  


#### Частина 2: Реалізація Deep Linking для Трекінгу Джерел Входу

**2.1. Мета Компонента Deep Linking**  
Компонент deep linking призначений для трекінгу джерел входу користувачів у Telegram-бот з зовнішніх ресурсів, таких як рекламні пости в x.com, Telegram-каналах, веб-сайтах або інших платформах. Це дозволяє збирати дані про ефективність рекламних кампаній, ідентифікувати ID кампаній та джерела трафіку (наприклад, "ad_xcom_nov2025_123"), а також пов'язувати ці дані з подальшими діями користувача в боті (кліки на реферальні посилання). Deep linking використовує вбудований механізм Telegram для передачі параметрів у посиланнях на бот (формат t.me/bot?start=payload), що забезпечує автоматичну обробку при першому запуску бота користувачем.  
- **Переваги:** Точне відстеження джерела без додаткових інструментів; інтеграція з БД для подальшої аналітики (наприклад, конверсія з реклами в кліки на біржі).  
- **Обмеження:** Працює тільки при першому вході або повторному /start з параметром; для існуючих користувачів без deep link source фіксується як "organic".  
- **Правила Використання:** Усі рекламні посилання повинні генеруватися з унікальним payload для кожної кампанії; уникати конфліктів ID кампаній; максимальна довжина payload — 64 символи (рекомендація Telegram).  

**2.2. Структура Посилань для Deep Linking**  
- **Формат Посилань:** Усі рекламні посилання повинні мати вигляд `https://t.me/YourYieldBot?start=адреса_payload`, де "YourYieldBot" — username бота.  
- **Структура Payload:** Payload повинен бути рядком у форматі "ad_platform_campaignID_extra", де:  
  - "ad_" — префікс для позначення рекламного джерела (обов'язково для фільтрації).  
  - "platform" — назва платформи (наприклад, "xcom", "telegram_ads", "website_banner").  
  - "campaignID" — унікальний ID кампанії (наприклад, "nov2025_123" — місяць/рік + номер).  
  - "extra" — опціональні параметри (наприклад, "_userhash" для префіл-ідентифікації, якщо потрібно).  
  - Приклад: "ad_xcom_nov2025_123" — для кампанії в x.com у листопаді 2025 з ID 123.  
- **Правила Генерації Посилань:**  
  - Генерувати посилання вручну для кожної кампанії.  
  - Забезпечити унікальність campaignID: Використовувати послідовну нумерацію (наприклад, 001, 002) у таблиці campaigns БД.  
  - Для тестування: Використовувати префікс "test_" (наприклад, "test_ad_xcom_001"), щоб відрізняти від реальних даних.   

**2.3. Обробка Deep Linking у Telegram Bot Service**  
- **Інтеграція з Aiogram:** Обробка відбувається в хендлері для команди /start з deep link.  
  - **Правила Обробки:**  
    - Якщо посилання містить payload — витягнути його та зберегти як acquisition_source у БД.  
    - Якщо payload відсутній — зафіксувати source як "organic".  
    - Перевірити, чи користувач вже зареєстрований: Якщо так, оновити source тільки якщо попередній був "organic" (щоб не перезаписувати рекламне джерело).  
    - Обробити помилки: Якщо payload невалідний (наприклад, не починається з "ad_") — логувати в таблицю logs як "warning: invalid_payload" та встановити source "unknown".  
  - **Дії Після Обробки:**  
    - Зберегти або оновити запис у таблиці users: telegram_id, hashed_id (генерувати хеш SHA-256 від telegram_id), acquisition_source, joined_at (якщо новий користувач).  
    - Надіслати вітальне повідомлення з урахуванням source (наприклад, "Вітаю! Ти прийшов з реклами в x.com (кампанія 123). Ось головна сторінка.").  
    - Оновити last_activity в таблиці users.  
- **Інтеграція з Data Service:** Після обробки deep link, бот повинен надіслати HTTP-запит до Data Service (endpoint /user/register або подібний) для збереження даних у БД.  
  - **Правила Запиту:** POST-запит з JSON: {"telegram_id": 123456, "source": "ad_xcom_nov2025_123"}. Data Service генерує hashed_id та зберігає.  

**2.4. Збір та Зберігання Даних про Джерела в БД**  
- **Таблиці, Які Залучаються:**  
  - users: Зберігати acquisition_source як повний payload (для детальної аналітики).  
  - campaigns: Автоматично створювати або оновлювати запис при новому campaignID (наприклад, витягнути з payload "nov2025_123" та додати platform="xcom").  
- **Правила Зберігання:**  
  - Уникати дублювання: Перед insert перевіряти існування користувача за telegram_id.  
  - Агрегація для Аналітики: Дозволити запити типу "Кількість користувачів з source LIKE 'ad_xcom_%'" для підрахунку по платформі.  
  - Безпека: Не зберігати оригінальний telegram_id у відкритих логах; використовувати hashed_id для всіх зовнішніх посилань (наприклад, у redirect).  
- **Додаткові Функції:**  
  - Якщо користувач повторно входить з іншим deep link — логувати в logs як "update_source_attempt", але не змінювати первинний source, щоб зберегти оригінальне джерело.   

**2.5. Тестування та Валідація Deep Linking**  
- **Сценарії Тестування:**  
  - Тест 1: Новий користувач з deep link — перевірити збереження source, hashed_id, joined_at.  
  - Тест 2: Існуючий користувач з новим deep link — не змінювати source, логувати спробу.  
  - Тест 3: Без deep link — source="organic".  
  - Тест 4: Невалідний payload — source="unknown", лог у logs.  
  - Тест 5: Масштаб: Симулювати 100 входів з різними campaignID — перевірити БД на дублі.  
- **Інструменти Тестування:** Використовувати самостійно згенеровані тестові акаунти Telegram; перевіряти БД через SQL-запити; моніторити запити до Data Service.  
- **Правила Валідації:** Усі дані повинні зберігатися в UTC; забезпечити, щоб deep link не впливав на швидкість завантаження бота (обробка <1 сек).  


#### Частина 3: Реалізація Власного Redirect Server для Трекінгу Кліків на Реферальні Посилання

**3.1. Мета Компонента Redirect Server**  
Власний redirect server є ключовим елементом для трекінгу взаємодій користувачів з реферальними посиланнями на біржі (наприклад, Binance, Bybit, Nexo), які розміщені в HTML-тексті повідомлень бота. Сервер діє як посередник: замість прямого посилання на біржу, бот генерує посилання на redirect-endpoint, який логує дані кліку (hashed_user_id, source, page, exchange, timestamp, ip_address, user_agent, ref_code) у базі даних PostgreSQL, а потім виконує HTTP-редірект (301 або 302) на оригінальне реферальне посилання біржі. Це забезпечує повний контроль над аналітикою кліків без залежності від зовнішніх сервісів, дозволяючи відстежувати повторні кліки від одного користувача, ефективність сторінок бота та конверсію з джерел реклами.  
- **Переваги:** Точність даних (кожен клік логувався з контекстом); інтеграція з deep linking (source передається автоматично); мінімальні затримки (менше 1 секунди на редірект); можливість додавати UTM-параметри для додаткової аналітики на боці біржі.  
- **Правила Використання:** Redirect застосовується тільки для реферальних посилань; не використовувати для внутрішніх посилань бота; забезпечити, щоб редірект не порушував політику бірж (наприклад, додавати параметри без зміни ref_code).  

**3.2. Структура Посилань для Redirect**  
- **Формат Посилань:** Усі реферальні посилання в боті повинні генеруватися динамічно у форматі `https://your-domain.com/ref?параметри`, де "your-domain.com" — домен сервера (з HTTPS для безпеки).  
- **Обов'язкові Параметри в URL:**  
  - "user" — hashed_user_id (хеш SHA-256 від telegram_id, для ідентифікації без витоку).  
  - "source" — acquisition_source з БД (наприклад, "ad_xcom_nov2025_123" або "organic").  
  - "page" — ідентифікатор сторінки: "1" для головної (/start), "2" для перегляду продуктів конкретної біржі, "N" для списку всіх бірж.  
  - "exchange" — назва біржі в lowercase (наприклад, "binance", "bybit", "nexo").  
  - "ref_code" — реферальний код біржі (ваш партнерський код, наприклад, "YOURBINANCECODE").  
- **Опціональні Параметри:**  
  - "extra" — додаткові дані (наприклад, "_product=btc" для специфікації монети).  
  - "utm" — для додавання UTM-тегів (наприклад, "utm_source=bot&utm_medium=ref&utm_campaign=page1").  
- **Правила Генерації Посилань у Боті:**  
  - Генерувати посилання в хендлерах Aiogram для відповідних сторінок (наприклад, при /start — page="1").  
  - Отримувати source та hashed_user_id з БД через запит до Data Service перед генерацією.  
  - Вставляти посилання в HTML-текст: <a href="{redirect_url}">Перейти на {exchange}</a>.  
  - Забезпечити унікальність: Для кожного повідомлення генерувати свіжий URL (але без додаткових timestamp, щоб уникнути дублювання логів).  

**3.3. Обробка Запитів на Redirect Server**  
- **Інтеграція з Data Service (FastAPI):** Redirect server реалізується як частина Data Service з окремим endpoint (наприклад, GET /ref).  
  - **Правила Обробки Запиту:**  
    - Витягнути всі параметри з URL (query params).  
    - Перевірити обов'язкові параметри: Якщо відсутні (наприклад, немає "user" або "exchange") — логувати помилку в таблицю logs як "error: missing_params" та редіректувати на fallback-сторінку (наприклад, головну біржі без ref_code).  
    - Логувати клік: Перед редіректом вставити дані в таблицю clicks БД.  
    - Отримати IP та user_agent з заголовків запиту (request.client.host та request.headers['user-agent']).  
    - Виконати редірект: Сформувати цільове посилання на біржу (наприклад, "https://{exchange}.com/ref?ref={ref_code}&{utm}"), використовуючи HTTP-відповідь з кодом 302 (тимчасовий редірект для трекінгу).  
    - Обробити помилки: Якщо БД недоступна — логувати в logs та все одно редіректувати (щоб не ламати користувацький досвід).  
  - **Безпека та Оптимізація:**  
    - Застосувати rate-limiting: Обмежити 10 запитів/хвилину на IP для захисту від зловживань.  
    - Валідація параметрів: Перевіряти, чи exchange в списку дозволених (наприклад, ['binance', 'bybit', 'nexo']) — якщо ні, логувати "warning: invalid_exchange".  
    - Кешування: Не кешувати redirect-запити, оскільки кожен клік унікальний.  
    - Логування: Для кожного запиту фіксувати в logs базову інформацію (без чутливих даних), якщо є помилки.  
- **Інтеграція з Ботом:** Бот не обробляє redirect безпосередньо — тільки генерує URL; сервер незалежний.  

**3.4. Збір та Зберігання Даних про Кліки в БД**  
- **Таблиці, Які Залучаються:**  
  - clicks: Основна таблиця для логів кліків (деталі в Частині 1).  
  - users: Перевіряти існування hashed_user_id перед insert (якщо немає — створити з source="unknown").  
  - logs: Для помилок обробки (наприклад, "error: db_insert_failed").  
- **Правила Зберігання:**  
  - Insert для кожного кліку: Не агрегувати на сервері — зберігати сирі дані, агрегацію робити в аналітиці.  
  - Автоматичне Оновлення: Після insert оновити last_activity в таблиці users для користувача.  
  - Агрегація для Аналітики: Дозволити SQL-запити типу "SELECT COUNT(*) FROM clicks WHERE source LIKE 'ad_xcom_%' AND exchange='binance' GROUP BY page" для аналізу ефективності сторінок.  
- **Додаткові Функції:**  
  - Підтримка Повторних Кліків: Логувати кожен, навіть якщо з тієї ж сторінки/біржі — для підрахунку "скільки разів" у звітах.  

**3.5. Тестування та Валідація Redirect Server**  
- **Сценарії Тестування:**  
  - Тест 1: Клік з бота (page=1) — перевірити лог у clicks, редірект на біржу, дані в БД (source, timestamp тощо).  
  - Тест 2: Повторний клік від користувача — перевірити множинні записи в clicks з різними timestamp.  
  - Тест 3: Невалідні параметри — перевірити лог у logs, fallback-редірект.  
  - Тест 4: З різних сторінок (1,2,N) — перевірити коректність page в БД.  
  - Тест 5: Масштаб: Симулювати 100 кліків з різними source/exchange — перевірити БД на цілісність, затримки <1 сек.  
- **Інструменти Тестування:** Використовувати Postman або curl для симуляції запитів; перевіряти БД через pgAdmin або SQL; моніторити логи сервера.  
- **Правила Валідації:** Усі timestamps в UTC; редірект повинен працювати на мобільних/десктопних браузерах; забезпечити, щоб сервер витримував навантаження (наприклад, 1000 запитів/хвилину).  


#### Частина 4: Інтеграція з Базою Даних та Аналітика Дій Користувачів

**4.1. Мета Інтеграції з Базою Даних**  
Інтеграція з базою даних PostgreSQL призначена для централізованого зберігання всіх трекінгових даних (джерела входу, кліки на реферальні посилання, історія дій користувачів), забезпечення цілісності даних та надання бази для аналітики. Це дозволяє пов'язувати дані з deep linking та redirect server, створювати звіти про ефективність кампаній, поведінку користувачів та конверсію. БД інтегрується з Data Service (для запису/читання) та Telegram Bot Service (через API Data Service), забезпечуючи асинхронну роботу без прямих запитів з бота до БД.  
- **Переваги:** Масштабованість (підтримка мільйонів записів); транзакційність (атомарні операції для уникнення втрат даних); безпека (ролі доступу, енкрипція).  
- **Обмеження:** Обмежити прямі запити з бота — все через Data Service для безпеки.  
- **Правила Інтеграції:** Використовувати ORM (наприклад, SQLAlchemy) в Data Service для абстракції; забезпечити бекапи БД (щоденні); моніторити розмір БД (архівувати старі дані).  

**4.2. Структура Інтеграції з БД**  
- **Компоненти Інтеграції:**  
  - **Data Service (FastAPI):** Основний шар для взаємодії з БД — endpoints для CRUD-операцій (create/read/update/delete).  
  - **Telegram Bot Service (Aiogram):** Надсилає запити до Data Service (HTTP POST/GET) для збереження/отримання даних; не має прямого доступу до БД.  
  - **Database Layer:** Розширений шар у Data Service для SQL-запитів, міграцій (Alembic) та конфігурації (підключення через DSN).  
- **Правила Підключення до БД:**  
  - Використовувати connection pool (для ефективності при високому навантаженні).  
  - Конфігурація: Хостинг на Railway/Fly.io з PostgreSQL addon; credentials в env-змінних (DB_USER, DB_PASS, DB_HOST).  
  - Міграції: Автоматично застосовувати при деплої (Alembic для створення/оновлення таблиць).  
  - Транзакції: Використовувати для операцій запису (наприклад, insert в users та clicks в одній транзакції).  
- **Потік Даних у Системі:**  
  1. Deep Linking: Бот обробляє /start → Надсилає POST до Data Service (/user/register) з telegram_id та source → Data Service генерує hashed_id та вставляє в users.  
  2. Redirect: Сервер обробляє клік → Прямо вставляє в clicks (асинхронно, щоб не затримувати редірект).  

**4.3. Деталі Таблиць та Зв'язків у БД**  
- **Розширення Таблиць (з Частини 1):**  
  - **users:** Додати колонку query_history (JSONB) — для зберігання історії запитів (наприклад, [{"symbol": "BTC", "timestamp": "2025-11-13T10:00:00"}]) для персоналізації.  
  - **clicks:** Додати колонку is_converted (BOOLEAN DEFAULT FALSE) — для майбутнього маркування конверсій (якщо отримано підтвердження від біржі).  
  - **campaigns:** Додати колонку total_users (INTEGER) та total_clicks (INTEGER) — для агрегованих метрик.  
  - **logs:** Додати колонку related_user (VARCHAR(64)) — посилання на hashed_user_id для фільтрації помилок по користувачах.  
- **Зв'язки Між Таблицями:**  
  - Foreign Key: clicks.hashed_user_id REFERENCES users(hashed_user_id) ON DELETE CASCADE (видаляти кліки при видаленні користувача).  
  - Індексація: Додати композитні індекси (наприклад, ON clicks (source, exchange, page)) для швидких аналітичних запитів.  
  - Типи Даних: Використовувати TIMESTAMP WITH TIME ZONE для всіх дат/часів; JSONB для гнучких полів (наприклад, extra_params в clicks).  
- **Правила Зберігання Даних:**  
  - Автоматична Генерація: hashed_id генерується в Data Service при insert.  
  - Валідація: Перед insert перевіряти дані (наприклад, exchange в списку дозволених; source не порожній).  
  - Архівування: Щомісяця переносити кліки старше 6 місяців в archive_clicks (окрема таблиця з тією ж структурою).   

**4.4. Тестування та Валідація Інтеграції та Аналітики**  
- **Сценарії Тестування:**  
  - Тест 1: Запис даних з deep linking — перевірити insert в users, коректність source.  
  - Тест 2: Запис кліків — симулювати redirect, перевірити clicks, зв'язок з users.  
  - Тест 3: Аналітичні запити — виконати SQL, перевірити результати (наприклад, conversion_rate = 0.5).  
  - Тест 4: Помилки — симулювати відмови БД, перевірити fallback (лог в logs, не ламати redirect).  
  - Тест 5: Масштаб — вставити 1000 записів, перевірити швидкість запитів (<100ms).  
- **Інструменти Тестування:** SQL-запити вручну; unit-тести в Data Service (Pytest); моніторинг (Prometheus для метрик БД).  
- **Правила Валідації:** Усі операції транзакційні; дані коректні (наприклад, timestamp в UTC); аналітика точна (порівняти з ручними підрахунками).  


#### Частина 5: Тестування, Розгортання та Підтримка Системи

**5.1. Мета Частини**  
Ця частина ТЗ описує процеси тестування системи трекінгу, розгортання на хостингу (hosting) з урахуванням початкового використання Docker для локального та тестового середовища, а також правила підтримки та моніторингу після запуску. Мета — забезпечити стабільність, безпеку та масштабованість системи, з можливістю переходу від контейнеризації (containerization) до прямого розгортання на реальному сервері. #### **2.1. Розширена Валідація та Парсинг Payload у Deep Linking**

**Доповнення до Розділу 2.2 Вашого ТЗ (Структура Payload):**

- **Багаторівнева Валідація Payload:**  
  - **Рівень 1 — Формальна Валідація:**  
    - Перевірка довжини: payload повинен бути 5-64 символи (мінімум для "ad_x_1", максимум згідно з обмеженням Telegram).  
    - Дозволені символи: `a-z`, `A-Z`, `0-9`, `_`, `-` (не дозволяти спецсимволи типу `&`, `=`, `/` для уникнення injection-атак).  
    - Regex-патерн: `^(ad|test)_[a-z0-9_-]+_[a-z0-9_-]+(_[a-z0-9_-]+)?$` (обов'язкові: префікс, платформа, campaignID; опціональний: extra).  
    - **Приклад валідних:** `ad_xcom_nov2025_123`, `test_telegram_ads_001_variant_a`.  
    - **Приклад невалідних:** `ad_xcom` (замало частин), `ad_x com_123` (пробіл), `ad_xcom_123&ref=hack` (спецсимволи).  
  
  - **Рівень 2 — Семантична Валідація:**  
    - Перевірка платформи: `platform` повинен бути в списку дозволених значень (whitelist): `['xcom', 'telegram_ads', 'facebook', 'reddit', 'website_banner', 'email_campaign', 'influencer']`.  
    - Якщо платформа не в списку — логувати "warning: unknown_platform" в `logs` з повним payload, встановити `acquisition_source` як `ad_unknown_{platform}_{campaignID}` для збереження даних, але позначити для майбутньої перевірки.  
    - Перевірка campaignID: Має бути унікальним в таблиці `campaigns`. Якщо campaignID вже існує з іншою платформою — логувати "warning: campaign_id_conflict" (можливо, помилка в генерації посилань).  
  
  - **Рівень 3 — Бізнес-Логіка Валідації:**  
    - Перевірка префіксу: Якщо payload починається з `test_` — зберігати дані в окрему тестову таблицю `test_users` замість `users` (щоб не забруднювати production-дані під час тестування).  
    - Якщо payload починається з `ad_`, але кампанія вже завершена (перевірка `campaigns.end_date < NOW()`) — логувати "warning: expired_campaign", але все одно зберігати source (можливо, користувач знайшов старе посилання).  
    - **Правило для Extra-Параметрів:** Якщо `extra` містить `_userhash`, витягнути його та порівняти з `hashed_id` для pre-fill identification (попередня ідентифікація користувача, якщо він вже був в системі). Якщо збіг — оновити `last_activity`, не створювати новий запис.

- **Обробка Спеціальних Символів та URL Encoding:**  
  - Telegram автоматично URL-кодує payload, тому необхідно декодувати перед обробкою: `urllib.parse.unquote(payload)`.  
  - **Edge Case:** Якщо користувач вручну редагує посилання та додає `%20` (пробіл) або інші закодовані символи — після декодування перевірити на відповідність regex-патерну з Рівня 1.  
  - **Правило:** Якщо після декодування payload невалідний — не зберігати як `acquisition_source`, встановити `source="malformed_deeplink"` та логувати в `logs` з оригінальним payload для forensics (судово-медичної експертизи).

---

#### **Доповнення до технічного завдання, Обробка Edge Cases (Граничних Випадків) у Deep Linking**

**Критичні Сценарії, Які Необхідно Обробити:**

- **Case: Дуже Довгий Payload (>64 символи)**  
  - **Сценарій:** Telegram відрізає payload після 64 символів, що може привести до втрати частини campaignID або extra.  
  - **Рішення:**  
    - Додати попередження в інструкціях для маркетингової команди: "Payload не більше 50 символів для безпеки".  
    - Якщо payload в боті саме 64 символи — логувати "warning: payload_at_limit" (можливо, відрізано).  
    - **Best Practice:** Використовувати короткі ID: замість `nov2025_123_variant_a_test` → `n25_123_va` (скорочення).

- **Case: Одночасні Запити /start від Одного Користувача (Race Condition)**  
  - **Сценарій:** Користувач швидко кліка "Start" двічі або мережа глючить, надсилаючи дублікати.  
  - **Проблема:** Можливий duplicate insert в таблицю `users`, що призведе до помилки `UNIQUE CONSTRAINT violation`.  
  - **Рішення:**  
    - В Data Service використовувати `INSERT ... ON CONFLICT (telegram_id) DO UPDATE` замість простого INSERT:  
      ```sql
      INSERT INTO users (telegram_id, hashed_id, acquisition_source, joined_at)
      VALUES ($1, $2, $3, NOW())
      ON CONFLICT (telegram_id) DO UPDATE
      SET last_activity = NOW();
      ```  
    - Це забезпечує idempotency (ідемпотентність) — повторні запити не створюють дублікати.  
  - **Правило:** Обробляти race condition на рівні БД, а не в коді бота (для надійності).

- **Case 5: Deep Link з Пустим Payload або Payload="start"**  
  - **Сценарій:** Користувач кліка на `t.me/YourYieldBot?start=` (пустий) або Telegram додає default `?start=start`.  
  - **Рішення:**  
    - Якщо payload порожній або `"start"` — розглядати як organic (без джерела).  
    - Встановити `acquisition_source="organic"` та не логувати як помилку.  
  - **Правило:** Виключити `"start"` зі списку валідних campaignID в таблиці `campaigns`, щоб уникнути конфліктів.

---

#### **Інтеграція з Таблицею Campaigns для Автоматичного Трекінгу**

**Доповнення до Розділу 2.4 Вашого ТЗ:**

- **Автоматичне Створення Запису в Campaigns:**  
  - При обробці deep link у Data Service перевіряти, чи існує campaignID в таблиці `campaigns`.  
  - Якщо немає — автоматично створити:  
    ```sql
    INSERT INTO campaigns (campaign_id, platform, start_date, description)
    VALUES ($1, $2, NOW(), 'Auto-created from deep link')
    ON CONFLICT (campaign_id) DO NOTHING;
    ```  
  - **Правило:** `end_date` залишити NULL (кампанія активна до закриття вручну адміністратором).  
  - **Альтернатива:** Вимагати попереднього створення кампанії в адмін-панелі перед генерацією посилань (більш контрольований підхід).

- **Валідація Активності Кампанії:**  
  - Перед збереженням `acquisition_source` перевіряти: `SELECT end_date FROM campaigns WHERE campaign_id = $1`.  
  - Якщо `end_date < NOW()` — логувати "warning: user_from_expired_campaign", але зберігати source (для аналізу "долгих хвостів").  
  - **Додаткова Метрика:** Додати колонку `late_entries_count` (INTEGER) в таблицю `campaigns` для підрахунку користувачів, які прийшли після завершення кампанії.

- **Агрегація Метрик Кампанії в Реальному Часі:**  
  - При кожному новому користувачі з кампанії оновлювати `campaigns.total_users`:  
    ```sql
    UPDATE campaigns SET total_users = total_users + 1 WHERE campaign_id = $1;
    ```  
  - **Правило:** Використовувати транзакцію для атомарності (insert в users + update в campaigns в одній транзакції).  
  - **Альтернатива:** Обчислювати `total_users` через SQL-агрегацію в аналітиці (щоб уникнути блокувань при високому навантаженні):  
    ```sql
    SELECT campaign_id, COUNT(*) as total_users 
    FROM users 
    WHERE acquisition_source LIKE 'ad_%' 
    GROUP BY campaign_id;
    ```

## 🔹 **Доповнення до ТЗ: Реалізація Повного Трекінгу Шляху Користувача**

### **Частина 6. Трекінг Дій Користувачів з Рекламних Посилань до Взаємодії з Біржами**

---

#### **6.1. Загальна Концепція Трекінгу**

Мета — побудувати **повну воронку трекінгу**, яка охоплює:

1. Джерело переходу користувача (через deep link з рекламних постів).
2. Поведінку користувача у боті (на яких сторінках взаємодіє з посиланнями на біржі).
3. Кліки на реферальні посилання (через власний Redirect Server).
4. Збереження всіх дій у БД PostgreSQL для подальшої аналітики.

Потік даних виглядає так:

> 🔗 **Реклама (x.com / Telegram / сайт)** → 🧠 **Deep Link** → 🤖 **Telegram Bot (Aiogram)** → 🌐 **Redirect Server (FastAPI)** → 🧾 **PostgreSQL (через Data Service)** → 📊 **Аналітика**

---

#### **6.2. Трекінг Взаємодій з Рекламних Посилань (Deep Linking)**

##### **Розширення функціональності deep linking:**

1. **Визначення рекламного джерела та кампанії:**

   * `source_type` → `"ad"` або `"organic"`;
   * `platform` → `"xcom"`, `"telegram_ads"`, `"website_banner"` тощо;
   * `campaign_id` → унікальний ідентифікатор (наприклад, `"nov2025_001"`).

2. **Збереження параметрів переходу:**

   * При вході через deep link зберігаються:

     * `telegram_id`, `hashed_user_id`, `source`, `campaign_id`, `platform`, `timestamp`, `first_entry_page="1"`.
   * Дані записуються в таблиці:

     * `users` (новий або оновлений користувач);
     * `campaigns` (оновлення `total_users`).

3. **Зв’язок з подальшими кліками:**

   * `acquisition_source` передається у всі подальші події користувача (через `hashed_user_id`).

4. **Відстеження часу взаємодії:**

   * Кожна сторінка в боті реєструє `last_activity` і `time_on_page` (через middleware Aiogram, який логуватиме, коли користувач відкриває сторінку та коли переходить далі).

---

#### **6.3. Трекінг Взаємодій у Telegram-Боті**

Кожна з трьох сторінок у боті має власну логіку трекінгу:

| **Сторінка** | **Позначення** | **Опис**                            | **Дані, що логуються**                                  |
| ------------ | -------------- | ----------------------------------- | ------------------------------------------------------- |
| 1            | `page=1`       | Головна сторінка (/start)           | `user_id`, `source`, `timestamp`, `session_id`          |
| 2            | `page=2`       | Перегляд продуктів конкретної біржі | `exchange`, `product_type`, `time_spent`, `click_count` |
| N            | `page=N`       | Список усіх бірж                    | `selected_exchange`, `click_timestamp`                  |

##### **Правила логування:**

* Для кожного відкриття сторінки створюється запис у таблиці `user_actions`:

  ```sql
  CREATE TABLE user_actions (
      id SERIAL PRIMARY KEY,
      hashed_user_id VARCHAR(64),
      source VARCHAR(255),
      page VARCHAR(10),
      action_type VARCHAR(50), -- open_page, click_exchange, etc.
      exchange VARCHAR(50),
      timestamp TIMESTAMP,
      metadata JSONB
  );
  ```
* При переході на сторінку з продуктами конкретної біржі фіксується додатково `exchange` і `product_type`.
* Якщо користувач натискає на посилання біржі, бот формує динамічний redirect URL, що включає всі контекстні дані (`source`, `page`, `exchange`).

---

#### **6.4. Трекінг Реферальних Кліків через Redirect Server**

##### **Нові вимоги до redirect-сервера:**

* Сервер має валідувати всі вхідні параметри (user, source, page, exchange, ref_code).
* Дані кліку зберігаються у таблиці `clicks` з додатковими полями:

  * `session_id` — UUID для групування дій одного користувача;
  * `time_from_entry` — час від першого запуску до кліку;
  * `is_first_click` — BOOL для першої взаємодії.

##### **Формат redirect-посилань (приклад):**

```
https://redirect.yieldbot.com/ref?user=hash_abc123&source=ad_xcom_nov2025_001&exchange=bybit&page=2&ref_code=BYBIT123
```

##### **Обробка на сервері:**

1. Отримати параметри → валідувати → записати в `clicks`.
2. Обчислити `is_first_click` через:

   ```sql
   SELECT COUNT(*) FROM clicks WHERE hashed_user_id=$1;
   ```
3. Додати поле `click_position` (номер кліку у сесії).
4. Перед редіректом:

   * Вставити дані у БД (`INSERT INTO clicks (...)`);
   * Повернути `302 redirect` на реферальне посилання.

---

#### **6.5. Запис Даних у PostgreSQL для Аналітики**

##### **Створення додаткових таблиць:**

```sql
CREATE TABLE user_sessions (
    id SERIAL PRIMARY KEY,
    hashed_user_id VARCHAR(64),
    source VARCHAR(255),
    session_id UUID DEFAULT gen_random_uuid(),
    session_start TIMESTAMP,
    session_end TIMESTAMP,
    total_clicks INT DEFAULT 0,
    total_time INT DEFAULT 0
);
```

##### **Логіка оновлення:**

* При кожному кліку → `total_clicks += 1`;
* При завершенні взаємодії → `session_end = NOW(); total_time = EXTRACT(EPOCH FROM (session_end - session_start));`.

##### **Аналітичні цілі:**

* Обчислення CTR по сторінках:

  ```sql
  SELECT page, COUNT(clicks.id)::float / COUNT(user_actions.id) AS ctr
  FROM user_actions
  JOIN clicks ON user_actions.hashed_user_id = clicks.hashed_user_id
  GROUP BY page;
  ```
* Аналіз активності користувачів за джерелами:

  ```sql
  SELECT source, COUNT(DISTINCT hashed_user_id) AS users, COUNT(clicks.id) AS total_clicks
  FROM clicks
  GROUP BY source;
  ```
