# 🔧 Технічне завдання на впровадження системи трекінгу дій користувачів у Telegram-боті EarnAggregator

## 🏗️ Загальна інформація про впровадження

### Мета впровадження:
- Створити систему трекінгу (tracking system) для відстеження дій користувачів Telegram-бота, таких як команди (/start, /yield <symbol>, /top), кліки на кнопки (button clicks), перегляди сторінок (page views) та реферальні переходи (referral clicks).
- Забезпечити запис ключових параметрів дій у базу даних PostgreSQL для аналізу поведінки користувачів, персоналізації рекомендацій (recommendations) та монетизації через реферальні програми (referral programs).
- Інтегрувати трекінг у існуючу архітектуру бота на Aiogram 3.x, з мінімальним впливом на продуктивність (performance), щоб час відповіді не перевищував 0.5 секунди.
- Підтримати масштабованість (scalability) для великої кількості користувачів (100+ одночасно), з використанням асинхронної обробки (asynchronous processing) та кешування (caching) для часто використовуваних даних.
- Монетизація: Використовувати трекінг для відстеження кліків на реферальні посилання (referral links) бірж (Binance, Bybit) та сервісів (Nexo), з записом статистики для розрахунку винагород.

### Джерела даних для впровадження:
- Результати пошуку на форумах (Stack Overflow, Reddit r/telegrambot): Обговорення про логування дій у Aiogram з базами даних (databases), наприклад, використання middleware для трекінгу повідомлень (messages) та callback queries.
- Приклади на GitHub: Репозиторії як MrConsoleka/aiogram-bot-template (з admin panel для моніторингу), aiogram-peewee-template (інтеграція з Peewee ORM для логування), 51n1au5k1/aiogram_clickhouse_bot_template (логування в ClickHouse, але адаптувати для PostgreSQL). На Stack Overflow приклади з SQLAlchemy для запису дій у БД.
- Додаткові джерела: Відео на YouTube про інтеграцію Telegram bot з PostgreSQL (наприклад, "Building a Telegram Bot with PostgreSQL Integration"), статті на Medium про middleware в Aiogram для трекінгу.

### Вимоги до впровадження:
- Трекінг повинен бути асинхронним (asynchronous), щоб не блокувати основний потік бота.
- Записувати тільки ключові параметри: user_id, action_type (тип дії), timestamp (час), details (деталі, наприклад, команда або клік).
- Використовувати PostgreSQL для зберігання, з таблицею user_actions для логів.
- Обробляти помилки з graceful degradation: при проблемах з БД логувати в файл або Redis.
- Оновлювати дані в реальному часі, з періодичним чищенням старих логів (наприклад, зберігати 30 днів).

## 📊 Аналіз системи трекінгу

### Основні дії для трекінгу:
- Команди (commands): /start, /yield <symbol>, /top, /all_<exchange>_products.
- Кліки на кнопки (button clicks): Навігаційні кнопки, реферальні посилання.
- Перегляди сторінок (page views): Завантаження головного меню, фільтрованих списків.
- Реферальні взаємодії (referral interactions): Кліки на посилання, реєстрації через рефералку.

### Ключові параметри для запису в БД:
- user_id: Унікальний ID користувача з Telegram.
- action_type: Тип дії (command, button_click, page_view, referral_click).
- timestamp: Час дії в UTC.
- details: JSON з деталями (наприклад, {"command": "/yield BTC", "symbol": "BTC"}).
- session_id: ID сесії для групування дій.

### Проблеми поточного стану:
- Відсутність трекінгу: Неможливо аналізувати поведінку користувачів для персоналізації.
- Відсутність логування в БД: Дані не зберігаються для статистики монетизації.

### Цільові показники:
- Час трекінгу: < 0.1 секунди на дію.
- Об'єм даних: 1-10 КБ на запис.
- Масштаб: Підтримка 1000+ дій на хвилину.

## ⚠️ Нюанси впровадження системи трекінгу

На основі пошуку на форумах (Stack Overflow: приклади middleware в Aiogram для логування) та GitHub (репозиторії з шаблонами Aiogram з базою даних):

- **Middleware для трекінгу**: Використовувати Aiogram middleware для перехоплення всіх оновлень (updates), щоб логувати без змін у handlers. На GitHub в aiogram-bot-template рекомендують router.middleware для асинхронного логування.
- **Асинхронний запис у БД**: Використовувати asyncpg або SQLAlchemy з async сесіями, щоб уникнути блокування. На Reddit r/telegrambot радять фонові задачі (background tasks) для запису, щоб не затримувати відповідь користувачу.
- **Безпека даних**: Зберігати тільки анонімізовані дані (user_id хешувати якщо потрібно); уникати зберігання чутливих даних (personal data). На Stack Overflow згадують GDPR compliance для EU користувачів.
- **Масштабованість**: Для великої кількості дій використовувати черги (queues) як Celery або Aiogram dispatcher для фонового запису. На GitHub в aiogram-peewee-template приклади з чергами для логів.
- **Помилки**: При проблемах з БД логувати в файл або Redis; на форумах радять retry logic з exponential backoff.
- **Персоналізація**: На основі логів генерувати рекомендації (recommendations), наприклад, якщо користувач часто шукає ETH, пропонувати релевантні Earn продукти.
- **Монетизація**: Трекінг кліків на рефералки для розрахунку винагород; на Reddit згадують UTM tracking для посилань.

## 📊 Правила трекінгу та запису в БД

- **Типи дій для трекінгу**: Команди, кліки, перегляди, рефералки; ігнорувати системні оновлення (system updates).
- **Ключові параметри**: Зазначені вище; деталі в JSON для гнучкості.
- **Запис у БД**: Асинхронний UPSERT для уникнення дублів; таблиця з індексами на user_id та timestamp.
- **Чистка даних**: Видаляти записи старше 30 днів scheduler'ом.
- **Анонімізація**: Хешувати user_id якщо потрібно для privacy.
- **Метрики**: Логувати тільки успішні дії; ігнорувати спам (spam) через rate limiting.

## 🔍 Доповнення до технічного завдання

### 1. Архітектура збору подій (Event Tracking Architecture)

**Проблема:** поточна архітектура фіксує події лише на рівні middleware.
**Рішення:** розділити трекінг на 3 рівні:

1. **Event Collector (middleware)** — приймає події від Aiogram update.
2. **Event Processor (черга)** — асинхронно обробляє та нормалізує події.
3. **Event Storage (PostgreSQL)** — зберігає події з урахуванням індексації.

**Доповнення до ТЗ:**

* Додати шар `event_queue` на базі Redis Streams або RabbitMQ (альтернатива – FastAPI BackgroundTasks), який прийматиме події з middleware і відправлятиме їх у фоновий обробник.
* Мета — розвантажити бот, забезпечивши фіксацію >1000 подій/хв без затримки відповіді користувачу.

---

### 2. Розширена структура збережених подій

**Проблема:** поточна таблиця зберігає обмежений набір даних.
**Рішення:** додати контекстні поля для аналітики.

**Доповнення до ТЗ:**

| Поле          | Тип         | Призначення                                     |
| ------------- | ----------- | ----------------------------------------------- |
| `user_id`     | bigint      | Ідентифікатор користувача Telegram              |
| `action_type` | text        | Тип дії (command, click, referral, error)       |
| `timestamp`   | timestamptz | Час події (UTC)                                 |
| `session_id`  | uuid        | Для групування дій користувача                  |
| `context`     | jsonb       | Додаткова інформація: мова, джерело переходу    |
| `ref_id`      | text        | Ідентифікатор реферала (якщо є)                 |
| `platform`    | text        | Telegram, WebApp тощо                           |
| `latency_ms`  | integer     | Час реакції системи (для метрик продуктивності) |

---

### 3. Логіка формування `session_id`

**Проблема:** сесії не відслідковуються — важко будувати воронку користувача.
**Рішення:** створювати `session_id` при кожному новому `/start` або поверненні після 30 хв бездіяльності.

**Доповнення до ТЗ:**

* Реалізувати генерацію `session_id` у Redis з TTL = 30 хвилин.
* Використовувати цей `session_id` для групування послідовних дій у PostgreSQL.

---

### 4. Категоризація дій користувачів

**Проблема:** усі дії записуються без чіткої категорії.
**Рішення:** створити систему тегів (`tags`) для аналітики поведінки.

**Доповнення до ТЗ:**

* Додати мапу категорій:

  * `onboarding` — перші дії після /start
  * `navigation` — переходи між сторінками
  * `interaction` — кліки на кнопки
  * `referral` — взаємодії з реферальними лінками
  * `error` — помилки обробки
* У `details` зберігати тег дії для подальшої сегментації.

---

### 5. Оптимізація продуктивності запису подій

**Проблема:** при великій кількості подій можливі затримки при записі у PostgreSQL.
**Рішення:** застосувати батч-запис.

**Доповнення до ТЗ:**

* Збирати події у Redis Stream з подальшим **batch insert** у PostgreSQL кожні 2–5 секунд (або при 100+ подіях у черзі).
* Для обробки черги використовувати `background worker` на FastAPI (або Celery task).
* Такий підхід зменшує кількість транзакцій у БД у 50–100 разів.

---

### 6. Метрики та аналітика

**Доповнення до ТЗ:**

* Інтегрувати `Prometheus + Grafana` для моніторингу:

  * `tracked_events_total` — кількість подій
  * `tracking_latency_seconds` — середній час запису
  * `db_inserts_per_minute` — кількість batch-записів
  * `error_rate` — відсоток помилок логування
* Логувати час від обробки update до запису у БД (latency).

### 8. Тестування системи трекінгу

**Доповнення до ТЗ:**

* Створити **unit-тести** для перевірки:

  * Коректності запису подій

  * Роботи scheduler для очистки логів
* Використати `pytest-asyncio` для асинхронних тестів.
* Імітувати >1000 подій/хв для навантажувального тесту (`locust`, `k6.io`).

### 9. Безпека та приватність

**Доповнення до ТЗ:**

* Вилучити або шифрувати будь-які персональні дані з `details`.
* Очищати логи при запиті користувача (“Forget me request”).
