# 🔧 Технічне завдання на оптимізацію завантаження сторінки 1 за командою /start в Telegram боті

## 🏗️ Загальна інформація про оптимізацію

### Мета оптимізації:
- Значно зменшити час завантаження сторінки 1 (головного меню) за командою /start, досягнувши цільового показника в 0.5 секунди або менше.
- Зменшити кількість API-запитів з 20+ до 1-3 на один виклик команди, щоб знизити навантаження на систему та уникнути перевищення лімітів API.
- Ввести багаторівневе кешування для повторюваних даних, забезпечуючи швидкий доступ без повторних обчислень або запитів до зовнішніх джерел.
- Оптимізувати кожну операцію в процесі генерації сторінки, фокусуючись на паралелізації, батч-обробці та мінімізації зовнішніх залежностей.
- Підтримати масштабованість для великої кількості користувачів (100+ одночасно), зберігаючи стабільність та низьке споживання ресурсів.
- Інтеграція повинна відповідати загальній архітектурі проекту: модульність, кешування в Redis, зберігання в PostgreSQL, REST API на FastAPI, Telegram бот на Aiogram 3.x.

### Джерела даних для оптимізації:
- Результати тестування продуктивності: час завантаження сторінки 1 (~3-5 секунд), повільні операції в функціях _format_top_10_section та _format_exchanges_quick_view.
- Аудит кешування: відсутність локального кешу в боті, неконсистентне кешування в API.
- Виявлені проблеми: надмірна кількість окремих API-викликів, відсутність кешування складених сторінок.

### Вимоги до оптимізації:
- Зберегти повну функціональність сторінки 1 (топ-10 продуктів, швидкий огляд бірж, навігаційні кнопки).
- Використовувати тільки існуючі API ендпоінти, але оптимізувати їх виклики через батч-запити та кеш.
- Обробляти помилки з graceful degradation: при проблемах з API використовувати кешовані дані.
- Ввести метрики для моніторингу часу виконання кожної операції.
- Перейти до автоматизованого оновлення кешу через scheduler, з TTL (час життя кешу) 5-10 хвилин для динамічних даних.

## 📊 Аналіз поточного стану завантаження сторінки 1

### Основні компоненти сторінки 1:
- Топ-10 продуктів за APY з усіх бірж (використовує get_yield_by_symbol для кожного trending coin).
- Швидкий огляд по біржам для пріоритетних монет (BTC, ETH, SOL, USDT) (використовує get_exchanges для кожної біржі).
- Навігаційні кнопки для різних типів продуктів (статичні, без затримок).

### Повільні операції:
- _format_top_10_section: 10+ окремих API-викликів, час ~2-3 секунди.
- _format_exchanges_quick_view: 10 окремих API-викликів з limit=1000, час ~1-2 секунди.
- Загальна: 20+ запитів, що призводить до накопичення затримок через мережеві запити та обробку відповідей.

### Проблеми кешування:
- Відсутність кешу на рівні бота для готової сторінки.
- Неконсистентне кешування в API: деякі ендпоінти кешуються, але /products та /exchanges не завжди.
- Відсутність інвалідації кешу при змінах даних.

### Цільові показники:
- Час завантаження: < 0.5 секунди.
- Кількість API-викликів: 1-3.
- Навантаження: Зменшити на 90% за рахунок кешу.

## ⚠️ Нюанси оптимізації завантаження сторінки 1

- **Багаторівневе кешування**: Кешувати не тільки окремі компоненти, але й готову сторінку, щоб уникнути повторної генерації. На форумах (Stack Overflow, Reddit r/fastapi) радять використовувати Redis для швидкого доступу з TTL 300 секунд.
- **Батч-запити**: Заміняти окремі виклики на групові, щоб зменшити мережеві затримки. На GitHub issues CCXT відзначають, що батч зменшує час на 70-80%.
- **Паралелізація**: Виконувати незалежні операції (наприклад, форматизація розділів) паралельно, але уникати надмірного навантаження на CPU.
- **Метрики**: Додавати логування часу для кожної операції, щоб виявляти вузькі місця в реальному часі.
- **Fallback**: При помилках кешу використовувати default дані або попередній кеш, щоб сторінка завжди завантажувалася.
- **Масштабованість**: Для великої кількості користувачів кешувати глобально, а не per-user, з персоналізацією тільки для критичних частин.
- **Тестування**: Перевіряти на різних навантаженнях (1-100 користувачів), моніторити мережеві запити в devtools.

## 📊 Правила оптимізації кожного елемента, процесу та дії

- **Оптимізація API-викликів**: Для кожного виклику перевіряти кеш перед запитом; використовувати батч-ендпоінти якщо доступні; обмежувати limit до необхідного мінімуму (наприклад, 10 замість 1000).
- **Оптимізація кешування**: Встановлювати TTL залежно від динаміки даних (5 хвилин для топ-10, 10 хвилин для оглядів); інвалідувати кеш при оновленні даних scheduler'ом.
- **Оптимізація форматування**: Виконувати паралельно розділи сторінки; уникати циклів з запитами всередині.
- **Оптимізація метрик**: Додавати timestamps на початок/кінець кожної операції; логувати тільки критичні затримки (>0.1 секунди).
- **Оптимізація помилок**: При помилках повертати кешовану версію; логувати без блокування потоку.

## 🔍 Додаткові рекомендації та доповнення до технічного завдання

### 1. Архітектурні зміни кешування

**Поточна проблема:** кешування розподілене між ботом та API без узгодженого TTL, інвалідації й системи метрик.
**Рішення:**

* Ввести **єдиний кеш-шар** (Redis Cluster) з розділеними просторами ключів:
  `bot_cache:*` — кеш сторінок,
  `api_cache:*` — кеш даних з API.
* Використати **єдиний CacheManager** (спільний модуль) для бота та API, який підтримує TTL, JSON-серіалізацію та lazy update.
* Додати **lock-механізм** (Redis SETNX) для уникнення одночасного оновлення кешу кількома процесами.

---

### 2. TTL стратегія та інвалідація

**Додати окрему таблицю TTL політик:**

| Дані                  | TTL (сек) | Інвалідація                             |
| --------------------- | --------- | --------------------------------------- |
| Топ-10 продуктів      | 300       | Автоматична при нових даних у /products |
| Огляд бірж            | 600       | При оновленні списку бірж               |
| Повна сторінка /start | 300       | Кожні 5 хв через scheduler              |
| Помилки API           | 60        | Автооновлення після хвилини             |

**Інвалідація:**
Використати **pub/sub Redis канал**, щоб API після оновлення даних надсилало повідомлення `invalidate:cache_key`.
Бот слухає цей канал і очищує кеш відповідної сторінки.

---

### 3. Паралелізація обробки

* Впровадити **`asyncio.gather()`** для паралельного отримання незалежних блоків (*top_10_section*, *exchange_quick_view*).
* Додати **обмежувач паралелізму (Semaphore)**, щоб уникнути перевантаження при 50+ користувачах одночасно.

---

### 4. Використання background scheduler

* Реалізувати **scheduler на рівні FastAPI** через `APScheduler` або `aiocron` для попереднього оновлення кешу.
* Запускати оновлення кешу **поза контекстом користувацьких запитів**, щоб не блокувати бот.

---

### 5. Кешування з lazy update

* Використати підхід **"stale-while-revalidate"**:

  * Якщо TTL минув, повертати старий кеш одразу користувачу.
  * Оновлення кешу — у фоні, без затримки для користувача.
* Така стратегія знижує пік навантаження при одночасних запитах.

---

### 6. Метрики та моніторинг

* Інтеграція з **Prometheus** через `fastapi-prometheus` або `prometheus_client`:

  * `request_duration_seconds`
  * `cache_hit_ratio`
  * `api_call_count`
* Налаштувати **Grafana dashboard** для візуалізації затримок `/start`.

---

### 7. Тестування продуктивності

* Використати **Locust** або **k6.io** для симуляції 100-1000 користувачів одночасно.
* Порівняти:

  * середній час відповіді до/після кешування;
  * кількість API-викликів;
  * коефіцієнт cache hit.

---

### 8. Додаткові оптимізації FastAPI

* Увімкнути **Uvicorn workers з `--workers=2-4`**.
* Використати **orjson** замість стандартного json для серіалізації.
* Увімкнути **gzip-компресію** відповідей API (`FastAPI.middleware.GZipMiddleware`).

---

### 9. Оптимізація структури кешу в Redis

* Зберігати ключі з **версією структури даних** (наприклад, `main_menu:v1:{user_id}`), щоб при зміні структури автоматично створювався новий кеш.
* Використати **Redis hash** для зберігання окремих блоків сторінки (*top10*, *exchanges*, *buttons*), щоб оновлення не вимагало інвалідації всієї сторінки.
